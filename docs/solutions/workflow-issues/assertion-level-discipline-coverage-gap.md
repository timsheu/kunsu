# 斷言層級紀律兩輪演進——掛載點覆蓋缺口、時效陷阱與讀寫雙態措辭

## Context

這條紀律經歷了兩輪事故才收斂為現在的形狀。

**第一輪（創始事件，2026-08-14，handoff v0.15.0）**：軍師 session 查閱 `pages-index.md`（一份中介索引文件）便當作查證完成，以事實語氣轉述其記載內容；被指正的一方原本是正確的，卻被這股「事實語氣」壓過而放棄自查、被說服改口。實害通道不是查證缺席本身，而是**二手資訊被以一手語氣轉述**——聽者無從分辨斷言背後的證據等級。v0.15.0 因此建立斷言層級紀律：查閱中介文件（規格、索引、對照表、交接、回覆）所得一律定義為二手；措辭義務全涵蓋（凡來源為中介文件即寫「依 X 記載」，不以「事實是」轉述）；查證義務分級（判準為「對方會不會據此寫程式或改設計」，據以實作級須一手落原始碼並註明方式與位置）；並於 done 收尾加入斷言自查（兩態逐筆點數、零筆顯式，使靜默單義化）。

**第二輪（2026-09-01 實證事故）**：軍師被問「公告訊號模式完成了嗎」，依 backend 回覆的自陳與 2026-08-22 交接「不含實作」的記載，下了「未完成」的結論。使用者憑記憶感到矛盾、質疑後查原始碼——功能其實已經完成，結論作廢。紀律存在、也曾生效，卻在這個時刻整組失守。

事故診斷出四個因素：

- **(a) 掛載點覆蓋缺口**——紀律掛在 add（寫交接時）、done 步驟 9（斷言自查）、規劃前盤點三處，而「對話中回答實作現況」這條路徑全不經過任何一處。同型失效 v0.15.0 已見過一次：信箱件數誤報同樣發生於對話回報時刻、不經工作流程步驟。
- **(b) 查證義務分級的縫隙**——對話評估情境下，session 容易自判「這不是據以實作級」而不查；但措辭義務若有被套用，第一句就該是「依 X 記載——未查原始碼」，即使結論仍錯，錯誤成本已大幅下降，因為聽者被明確告知證據等級。
- **(c) 宣告 ≠ 現況**——交接與回覆的記載是**時點快照**，實作可能在快照之後發生。把宣告層當現況層讀，是這次事故的直接成因。
- **(d) 既有原則句的範圍限制**——「自身狀態不憑記憶」原則句明文限於自身 repo，不涵蓋對子專案現況的斷言。

四個因素合起來指向同一個結構問題：單態設計下，「忘了標記的斷言」與「一手查證後的斷言」**完全同形**，失效不可觀察，只能靠使用者記憶對撞才會被抓到。

## Guidance

解法是讀寫雙側一組的設計（handoff v0.21.0 落地）——單做任一側都留缺口。以下寫成可移植的做法，kunsu 的具體落點作為例證。

**一、雙態措辭規則（讀方）**：對他方系統的現況斷言，措辭**必居兩態之一**——

- 「依 X 記載（未查原始碼）」：來源為中介文件，明示未經一手查證；
- 「已查」＋註明方式與位置（如「抽查某檔某段」）：一手查證過，並留下可覆核的痕跡。

關鍵在於：**無標記的現況斷言本身即屬可一眼辨識的違規形狀**。規則自帶理由句（宣告是時點快照，實作可能在其後發生），符合「harness 不做枷鎖」前提——帶理由的慣例、信任模型判斷，而非 hook 強制；開放式查證行為本來就無機械可判的攔截條件可寫。kunsu 落點：軍師範本副官慣例區新增原則句「子專案實作現況以原始碼為準」。

**二、寫方附主要修改檔案路徑清單**：涉程式碼改動的回覆，投遞前附上主要修改檔案的路徑清單。適用條件用**事實條件劃界**，不用回覆類別白名單——因為類別由被約束方自判，且 blocked 常是「改到一半」：

- 投遞前有程式碼改動即附，不論 `status` 為何；
- blocked 附卡關前已改的檔案；
- 暫離回報以 branch 名為既有錨點，明文免除；
- 答疑、拒絕等無碼回覆自然免除（無碼可附）。

「主要」的粒度＝**足供發起方定點抽查的代表性檔案**，不是窮舉 diff。分階段回覆列本次投遞前的新改動，歷次以序列聯集為準。清單的價值在把查證成本從「全庫搜尋」降為「定點抽查」；但清單本身仍是宣告層快照，**不能取代讀方句**——依賴方向是：讀方句觸發查證決策，寫方清單降低執行成本。

**三、掛載點選擇**：紀律只在必經路徑生效。設計 norm 時先問「失效最常發生在哪個時刻」，再檢查該時刻經過哪些載體。本案的教訓是「對話中回答現況」不經過任何工作流程步驟，所以掛載點必須選在 session 常駐可見的載體（範本原則句進 CLAUDE.md 層），而非只掛在特定子指令內。

**四、可觀察化設計原則**：norm 的失效偵測面必須讓「靜默單義化」——靜默只能有一種含義。雙態設計治的正是 adversarial review 抓出的「判別器與被測現象共用失效通道」問題：單態下忘了標記與查證完成同形；雙態下「無標記」成為違規訊號本身。這與 done 斷言自查的「零筆顯式」同構：零筆時必須顯式寫一行「本輪無他方系統斷言」，使靜默只剩「查核未執行」一種含義。

**五、多副本定型文字的防漂移載體**：寫方條款有四個副本（SKILL reply 步驟 2 為唯一權威、`new-handoff.sh` printf 定型行、SKILL 範例段定型行、`new-handoff-reply.sh` stderr 逐字同句＋補救指引「發現漏附可直接補進本回覆檔——尚未 commit、作者是你」）。防漂移用 consistency-check 錨句：C 項實跑產檔比對兩副本；新增 K 項**實跑 reply 腳本比對 stderr**——刻意不用靜態原始碼字面比對，因為執行期實測發現 `echo` 雙引號下反引號會被指令替換、stderr 實際印出殘句，而靜態字面比對會假 PASS（靜態比對看不見引號語意）；H 鏈補「以原始碼為準」字串，罩範本與三 live 軍師遷移。

## Why This Matters

**錯誤結論的系統後果**：把過期宣告當現況，產出的不只是一句錯話——軍師據此做規劃決策，可能重複派發已完成的工作（2026-09-01 事故若未被質疑，下一步就是為已完成的功能開交接）、或在錯誤前提上疊加設計。更深一層，未標記的斷言會**跨交接流傳**：交接本體是定案快照，一句以事實語氣寫入的二手轉述，會被後續 session 當一手事實引用，錯誤認知從單點污染變成鏈式擴散——這正是創始事件「事實語氣壓過對方自查」實害通道的放大版。

**可觀察化前後的偵測成本對比**：雙態設計前，抓到一次失效需要「使用者恰好記得矛盾的事實、恰好當場質疑、恰好去查原始碼」三個偶然疊加——2026-09-01 事故正是靠這條低機率路徑才被發現，意味著同型錯誤大概率曾靜默通過。雙態設計後，矛盾偵測成本降為「一眼可見的措辭標記」：看到一句現況斷言沒有「依 X 記載」也沒有「已查＋位置」，任何讀者（使用者或後續 session）不需要任何領域知識就能判定違規。偵測門檻從「知道正確答案」降為「認得句型」，這是一個量級的差距。

寫方清單的成本結構同理：全庫搜尋級的查證不會在對話節奏中實際發生，定點抽查級的才會——「順手查證」是否成立，取決於執行成本是否低到不打斷當下工作。

## When to Apply

- **對他方系統的現況做斷言時**——任何「X 功能做完了嗎」「Y 專案現在支不支援 Z」類問答，尤其在對話時刻（不經工作流程步驟的路徑）；自身 repo 以外的一切 repo 都算他方系統。
- **讀交接、回覆、規格、索引等中介文件並準備轉述時**——先分辨這句話要以哪一態出口。
- **撰寫涉程式碼改動的回覆時**——依事實條件（有碼即附）判斷是否附主要修改檔案清單。
- **設計新 norm 的失效偵測面時**——檢查「遵守的產物」與「忘記遵守的產物」是否同形；同形即失效不可觀察，考慮雙態化或零筆顯式化。
- **為紀律選掛載點時**——列舉失效實際發生的時刻，核對該時刻經過的載體；只掛在子指令內的紀律罩不住對話路徑。
- **落地多副本定型文字時**——建立唯一權威副本＋機械比對錨句；凡文字經過 shell 產生（printf／echo），比對必須走執行期實跑而非靜態字面。
- **收到帶現況斷言的訊息時（讀者側）**——無標記斷言視為證據等級未知，據以決策前先要求標記或自行查證。

## Examples

**違規 vs 合規措辭（2026-09-01 事故重演對照；檔案路徑為示意）**：

> 違規（事故原句型）：
> 「公告訊號模式**未完成**——backend 回覆與 08-22 交接都說不含實作。」
>
> 合規・第一態（未查，明示證據等級）：
> 「**依 2026-08-22 交接與 backend 回覆記載（未查原始碼）**，當時不含公告訊號模式實作；記載是時點快照，其後是否已實作需查原始碼確認。」
>
> 合規・第二態（已查，附方式與位置）：
> 「**已查**——抽查 `NotificationService.kt` 的 signal mode 分支與對應測試，公告訊號模式已實作。」

第一態即使結論仍錯，讀者已被告知這是宣告層資訊，不會把它當現況層採信；第二態則留下可覆核的查證痕跡。兩態之外的裸斷言，一眼即知違規。

**寫方清單實例（路徑為示意）**：

> 「本次修改主要落在：
> - `app/src/main/java/.../NotificationService.kt`（訊號模式分支）
> - `app/src/main/java/.../AnnouncementRepository.kt`
> 供定點抽查；非窮舉 diff。」

**echo 反引號陷阱 before/after**（consistency-check K 項採實跑比對的原因）：

> Before（腳本內定型行，雙引號包裹）：
> ```bash
> echo "投遞前有程式碼改動時，回覆請附主要修改檔案路徑清單（不論 \`status\`…）" >&2
> ```
> 靜態讀原始碼，字面看似與 SKILL 副本一致；但 bash 雙引號內的反引號是**指令替換語法**，執行期 stderr 實際印出的是殘句（並嘗試把 `status` 當指令執行）。靜態字面比對假 PASS，執行期實測才會抓到——靜態比對看不見引號語意。
>
> After（實際修法）：腳本側改用單引號 `printf '%s\n' '…' >&2` 確保反引號以字面輸出；consistency-check K 項實跑 `new-handoff-reply.sh`、擷取 stderr 實際輸出與 `new-handoff.sh` 產出檔的定型行逐字比對。比對對象是**執行結果**，不是原始碼字面。
