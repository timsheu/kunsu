# 回覆內容路由與收尾殘項清點——需求文件

## Summary

在既有收尾與彙整時刻加三道輕量查核，補上「回覆讀完後內容各自去哪」的流程缺口：kunsu-inbox 軍師模式回報新回覆／新上報時附分流提示行（第一攔截點）、handoff done 通讀回覆時一併執行反向路由查核（協議層兜底，抓指向發起方或第三方的行動項與已解答的既有疑問）、todo 標記已解決前清點檔內未完成殘項（`/todo` done 對稱）。全部僅提示不自動執行、零觸發詞、零範本改動、免 live 軍師遷移。

---

## Problem Frame

軍師流程定義了「交接 → 回覆 → 收尾」的完整生命週期，但沒有定義回覆讀完之後、內容各自的去處。回覆檔實際承載四類內容，現行機制只給其中兩類落點：工作結論（done 逐項驗收）與對他方系統的事實陳述（查核紀律）；「已解答的既有疑問」與「指向軍師自身的行動項」完全沒有落點，只靠當次 session 記憶承載。

ebook 軍師 2026-08-13 的檢討記錄了兩起實例：backend 六天前的回覆早已附上完整查詢途徑，軍師收尾歸檔後遺忘、差點重複發交接去問（事件三）；backend 明確標示「Apple Developer 帳號開辦需要你協調」，軍師收尾後零處置紀錄、懸空六天（事件四）。時間線查證確認：兩份交接同日建立、回覆抵達、done 收尾，含行動項的回覆在收尾當下就是最新回覆、已在逐項驗收查核的讀檔範圍內——回覆被讀了，但查核只比對「交接問題清單 vs 接手方交付」，反向內容落在查核面之外。

三實例查證確認缺口屬系統層面而非 ebook 特有：ivm 51 份回覆中 19 筆指向軍師的行動項有 16 筆路由明確，但出現一筆更隱蔽的變體——行動項曾路由進 todo 的「下一步」段，該 todo 整檔標「已解決」歸檔時殘項未逐項清點、隨檔靜默蒸發；另有一筆上報懸空 33 天，顯示缺口不限於回覆信箱。px 33 份回覆逾 20 筆行動項全數路由、零漏接，但靠的是三種 kunsu 未規定的自建紀律（逐回覆彙整 commit、裁決過堂、playbook 收容待決事項）——不漏是軍師個體紀律的產物，不是流程保證。

## Key Decisions

- **分流查核採雙層，複用既有分工先例**：kunsu-inbox 提示行（知悉層，彙整當下生效，涵蓋回覆與上報兩信箱）＋ handoff done 反向路由查核（協議層，必經流程兜底）。七個查證案例中六個源自回覆、一個源自上報，蒸發時刻集中在「掃到→彙整→歸檔」的彙整當下與 done 收尾兩點；inbox 既有「→ 收尾提示行」已建立「inbox 提示、handoff 執行」的分工模式，本次為同模式複用而非新架構。
- **攔截押在收尾與彙整時刻，不做每次彙整的強制分流儀式**：接受「交接遲不收尾就晚攔」的殘餘風險——積壓本身已有 SessionStart hook 與軍師沙盤的可見度兜底；換取零日常儀式成本。憲章層強制分流（範本工作流程改動）明列 deferred。
- **行動項不分指向**：指向發起方與指向第三方的行動項用同一道查核涵蓋，落點同為 todo 或轉交接。第三方指向已有實例觀察（px「請轉知 web-client-v2」型），單獨立類的成本換不到額外攔截力。
- **疑問回填靠語意判斷，不引入疑問識別碼**：識別碼（類 issue 編號）增加所有交接的撰寫成本，換到的比對保證仍需語意判斷兜底，不划算。誤報與漏報以「字面存在即提示、由使用者裁決」的傾向處理，比照沉澱訊號查核慣例。
- **寫方標記不做**：查證證據顯示寫方訊號從來不缺（事件四以引言區塊明確標示、ivm「待你裁示」措辭清楚），失效點全在讀方沒接；在回覆定型文字加標記段是對症狀不對根因。

## Requirements

**kunsu-inbox 分流提示行**

- R1. 軍師模式回報新回覆與新上報時，各段附一行分流提示：提醒彙整時判斷「指向軍師的行動項→落 todo 或轉交接；解答既有疑問→回填至該疑問所在文件」。形式比照既有「→ 收尾提示行」，僅提示、不新增互動、不改變掃描與 tripwire 邏輯。

**handoff done 反向路由查核**

- R2. done 通讀全部回覆時（沉澱訊號查核建立的既有讀檔範圍，無新增讀檔）一併判斷兩類反向內容：(a) 行動項——回覆中要求發起方協調、安排、處理某事，或建議讓第三方知悉，且不屬接手方自身的後續工作；(b) 已解答的既有疑問——回覆內容回答了本 repo todo、plan 或其他交接中登記過的疑問或承諾。
- R3. 有命中時隨逐項驗收結果一併回報，逐筆提示落點（行動項→todo 或新交接；答案→回填原疑問文件），由使用者決定是否當場處理；查核不自動建檔、不自動編輯任何文件。無命中靜默。
- R4. 查核結果在驗收查核當下回報，不延後到收尾完成——使用者暫緩收尾時，已發現的反向內容仍已顯式呈現，不隨暫緩消失。

**todo 收尾殘項清點**

- R5. handoff done 的 todo 收尾執行把 todo 標「已解決」前，掃描該檔內未完成子項（「下一步」「待辦」等段落中未註記完成的項目）；有殘項時逐項回報，由使用者決定一併視為已解決、轉出為新 todo、或保留不歸檔。
- R6. `/todo` done 子指令對稱加同款殘項清點。todo 檔案格式零改動，殘項辨識屬語意判斷、不強制新的標記慣例。

**落點與同步**

- R7. 改動落點僅 `skills/handoff/SKILL.md`、`skills/todo/SKILL.md`、`skills/kunsu-inbox/SKILL.md` 三份；軍師範本、上報歸檔四步驟、`status`／`verify` 值域、掃描腳本與 tripwire 零改動，免 live 軍師遷移。
- R8. handoff 與 todo 版號升版，kunsu-inbox 依賴聲明同步；CONCEPTS.md「done 收尾」詞條於實作時同步補述本查核。

## Acceptance Examples

- AE1. **Covers R2, R3.** 回覆末尾以引言區塊標示「開辦 Apple Developer 帳號的權限不在 backend 這端，請安排由有該權限的人執行」（事件四重演）。done 反向路由查核列出該行動項並提示落 todo；使用者確認後自行建立 todo，查核不代建。
- AE2. **Covers R2, R3.** 回覆載明後台平台欄位已上線可用並附重現步驟，而本 repo 另一份交接曾承諾「軍師會向 backend 取得查詢途徑」（事件三重演）。查核指出該疑問的答案已存在於本回覆，提示回填至承諾所在文件。
- AE3. **Covers R5.** done 一併收尾某來源 todo，該檔「下一步」段有兩項未註記完成（ivm 4K 型重演）。清點逐項列出，使用者選擇將其一轉出為新 todo、另一併同視為已解決。
- AE4. **Covers R1.** 軍師模式掃到一份新上報，內含「使用者會另外評估」的觀察項（ivm xlsx 型）。inbox 回報附分流提示行；session 彙整時識別該行動項並提示落 todo。
- AE5. **Covers R3.** 回覆僅含工作結論、逐項驗收全數命中、無反向內容。反向路由查核零輸出，done 流程與現行完全一致。

## Scope Boundaries

- 憲章分流慣例（範本工作流程強制四類分流）：deferred——等收尾查核實跑後再評估是否需要提前攔截點。
- 寫方標記段（回覆定型文字新增「給發起方的事項」段）：不做，理由見 Key Decisions。
- 疑問識別碼（類 issue 編號的可追蹤標識）：不做，理由見 Key Decisions。
- px 三紀律升格為強制規範：不做——留作 solutions 參考範本，是否沉澱另由 `/ce-compound` 流程決定。
- 申請信箱：不納入查核範圍——審核制結構化流程，三實例查證零觀察案例。
- 「交接遲不收尾」的積壓問題：非本案範圍，既有 SessionStart hook 與軍師沙盤已提供可見度。

## Dependencies / Assumptions

- 依賴：done 通讀全部回覆的讀檔範圍（沉澱訊號查核，handoff v0.10.0）已上線，反向路由查核附掛其上、無新增讀檔成本。
- 假設：行動項與殘項的辨識屬語意判斷，無法以字串比對保證；「字面存在即提示、由使用者裁決」的傾向使漏報偏向極小化，雜訊由摘要收斂控制。
- 假設：todo 為軍師自身行動項的預設落點（含無 plan 的純交接鏈工作線），不強制為每條工作線建立 plan。
