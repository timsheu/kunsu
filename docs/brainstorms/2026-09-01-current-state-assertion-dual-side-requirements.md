# 實作現況斷言的讀寫雙側補強 — 需求文件

## Summary

一組兩件的慣例補強：讀方——軍師範本新增原則句「子專案實作現況以原始碼為準」，斷言措辭必居兩態（依 X 記載（未查）／已查並註明方式與位置）；寫方——投遞前有程式碼改動的交接回覆附主要修改檔案路徑清單，掛載於交接本體「回覆方式」定型文字、handoff SKILL reply 指引與回覆產檔腳本 stderr 指路行。

---

## Problem Frame

實證事故（2026-09-01，ebook 軍師 session）：使用者問「公告訊號模式完成了嗎」，軍師依 backend 回覆自陳與 08-22 交接「不含實作」的記載下結論「未完成」；經使用者以記憶矛盾質疑後查原始碼，確認功能已完成，原結論作廢。

診斷為掛載點覆蓋缺口，非機制缺席：

- 斷言層級紀律（handoff v0.15.0）已明文「中介文件＝二手、據以實作級斷言須一手落原始碼」，但其掛載點為 add（寫交接時）、done 步驟 9（斷言自查附句）與規劃前既有盤點（工作流程步驟 2）——「對話中回答子專案實作現況」不經任何一個。
- 與 v0.15.0 已知失效形狀同型（自身狀態誤報 11 實 7 亦發生於對話回報時刻），但「子專案實作現況」無等價腳本可掛觸發詞：現況權威是原始碼，查證是開放式行為，不是一條指令。範本既有的「自身狀態不憑記憶」原則句，範圍明文限「自身 repo 狀態的具體數字或清單」，不涵蓋子專案。
- 加重因素一：查證義務分級設計下，對話評估易被自判為非據以實作級而不查；但措辭義務若被套用，第一句即應為「依 X 記載——未查原始碼」，錯誤成本大幅降低。
- 加重因素二：宣告不等於現況的時效陷阱——「不含實作」是時點快照，其後實作已發生；與 v0.15.0 創始事件（查 `pages-index.md` 當查證）同族。

寫方側的既有落差：reply 步驟 2 已有「盡量附可查核證據」指引，但只存在於 SKILL.md，接手方手動寫回覆時不經過；接手方必經的文本是交接本體尾端的「回覆方式」定型文字（`new-handoff.sh` 產生，腳本載體實測從未失效），該段目前對證據隻字未提。

---

## Key Decisions

- **讀寫兩側一組落地，單做任一側都留缺口。** 讀方句治本次事故根因（把過期宣告當現況）；寫方清單降查證成本（從全庫搜尋變定點抽查），使對話時刻順手查證的機率實際上升。修改清單本身仍是宣告層快照，故不能取代讀方句。
- **掛載點依載體觸及率選定。** 寫方掛交接本體定型文字——接手方必經文本、腳本產生；另掛 `new-handoff-reply.sh` stderr 指路行——「手動路徑＋舊交接」情境下唯一觸及的載體；stderr 於產檔後印出、屬事後提醒（內文走 stdin 先定稿），條款行須附補救指引（發現漏附可直接補進剛建立的回覆檔——尚未 commit、作者是自己）；讀方掛軍師範本 CLAUDE.md——熟練軍師 session 僅存的必經載體。細節單一副本留 SKILL，定型文字只加一行並指回（指路牌模式）。
- **寫方條款以事實條件劃界。** 凡回覆投遞前有程式碼改動即附清單，不論回覆 status（blocked 附卡關前已改檔案）；暫離回報維持最小三要素，branch 名即為可查錨點故明文免除；純答疑、拒絕因無碼可列自然免除，不設類別白名單。
- **帶理由的慣例，不做行為強制。** 不以 hook 驗證回覆格式——開放式查證行為無機械可判的攔截條件，且違反「harness 不做枷鎖」前提。原則句與條款自帶理由，信任模型判斷。
- **清單粒度為「主要檔案」，非機驗窮舉。** 目的是給發起方可定點抽查的錨點，不是完整 diff 清單；不要求附 `git diff --stat` 輸出。

## Requirements

**讀方（軍師端）**

- R1. 軍師範本 `skills/kunsu-init/assets/templates/kunsu-claude.md` 副官慣例區、「自身狀態不憑記憶」原則句旁，新增姊妹原則句：子專案實作現況以原始碼為準；對其斷言措辭必居兩態之一——「依 X 記載（未查原始碼）」，或「已查」並註明查證方式與位置（如抽查某檔某段）。無標記的現況斷言即屬可一眼辨識的違規形狀。
- R2. 原則句自帶理由（宣告是時點快照，實作可能在其後發生），定位為能力提示與措辭義務，非行為強制。
- R3. 三 live 軍師（ebook／ivm／px）CLAUDE.md 同句同步遷移，四副本逐字一致，沿用 grep 恰中一次的遷移紀律。
- R4. `scripts/consistency-check.sh` 加入該句的比對字串，防範本與 live 軍師單側漏遷不可見。

**寫方（接手方端）**

- R5. 交接本體「回覆方式」定型文字新增一行：涉及程式碼改動的回覆，請附主要修改檔案路徑清單；以一行為限，細節指回 handoff SKILL reply 段。
- R6. 定型文字兩副本（`skills/handoff/scripts/new-handoff.sh` printf 與 `skills/handoff/SKILL.md` 範例段）逐字一致；R5 新行比照既有錨句慣例納入 consistency-check C 項比對清單，使兩副本的新行進入實跑逐字比對，既有比對維持通過。
- R7. SKILL.md reply 步驟 2 由「盡量附證據」升格為條件式結構要求：涉及程式碼改動時，主要修改檔案路徑清單為回覆必要內容；測試輸出、日誌、commit hash 維持既有「盡量附」地位。
- R8. 適用條件為事實條件：回覆投遞前有程式碼改動即附主要修改檔案清單，不論回覆 status（blocked 附「卡關前已改檔案」）；暫離回報維持最小三要素、以 branch 名為可查錨點明文免除；答疑、拒絕無程式碼改動自然免除。
- R10. `new-handoff-reply.sh` stderr 指路行的指引枚舉補「主要修改檔案清單」，條款一行以內文（非僅指標）形式印出並附補救指引一句（stderr 屬產檔後的事後提醒）；consistency-check 比對字串一併涵蓋此副本。

**版號與依賴同步**

- R9. handoff SKILL.md frontmatter 版號遞增，kunsu-inbox 依賴聲明同步；不涉掃描慣例、`status`／`verify` 值域與歸檔形狀，均零改動。

## Acceptance Examples

- AE1. **Covers R5, R7.** 接手方完成實作後回覆交接：回覆內文含「主要修改檔案」段，列出代表性檔案路徑。軍師日後被問該功能現況時，可依清單定點抽查原始碼，不需全庫搜尋。
- AE2. **Covers R8.** 接手方投遞暫離回報：內文僅 branch 名、一句現況、回來意向三要素，不附檔案清單——branch 名即為發起方可查錨點，不構成違反條款。
- AE3. **Covers R1, R2.** 軍師被問「XX 功能完成了嗎」，本輪僅讀過交接與回覆：回答措辭為「依 X 回覆記載已完成（未查原始碼）」，或先依回覆所附路徑抽查原始碼、以「已查」措辭作答並附查證方式與範圍。
- AE4. **Covers R1（事故重演檢驗）.** 交接記載「不含實作」、其後實作已發生的情境：軍師依 R1 措辭作答時，使用者能立即辨識結論依據為過期文件，矛盾偵測成本自「使用者記憶對撞」降為「一眼可見的措辭標記」；無標記的現況斷言（既無「依 X 記載」也無「已查」）依 R1 屬可辨識違規形狀，使用者應視為未查證處理。

## Scope Boundaries

- 舊交接本體的定型文字不回填——內文不可變（Invariant #5），寫方條款經定型文字僅及新產交接；對舊交接的回覆，skill 路徑受 R7 約束，手動腳本路徑由 R10 的 stderr 指路行觸及。
- 不解「軍師漏讀回覆」的訊息時效問題——本案只治措辭紀律與查證成本，回覆未被讀取的情境另屬掃描與收尾機制範疇。
- 不做行為強制：不新增 hook 驗證回覆格式，不擴 PreToolUse 守門範圍。
- 上報（`/kunsu-report`）與申請（`/kunsu-apply`）投遞不納入——僅交接回覆適用。
