# 交接前置規劃深度的張力：Uncle Bob 反 SDD 論點對照跨 repo 介接規格前置

Uncle Bob 不看好規格驅動開發：把一切想周全再動手形同瀑布，Agent 擅長寫華麗計畫卻常無法照著實作，往往回頭重寫重跑，前期規劃成為流程最貴的一段；蓋房子先畫完美設計圖是因為重來成本極高，Agent 改程式又快又便宜，或許更適合敏捷。

## 背景 / 動機

**kunsu 側的證據兩面**

- 支持他的：2026-07-25 ebook 軍師處理「已購書籍排序」時漏查自家歷史，過度規劃至使用者人工介入才收斂。
- 反對他的：跨 repo 場景的重做成本含協調成本，API 契約前置讓多方不必來回，這正是軍師存在的理由。Uncle Bob 的「重做便宜」論點以單一 codebase 為前提。

**觀察題**

- 哪些交接的前置規劃深度超過需要？可從已歸檔交接看「plan 篇幅」對照「回覆翻案次數」，找出規劃深度與實作落差的關係。
- 範本工作流程第 5 步「下筆交接前先確認議題已想透」是否需要加一句邊界：介接規格前置、實作細節不前置。

暫不改任何檔案，留作觀察項。
